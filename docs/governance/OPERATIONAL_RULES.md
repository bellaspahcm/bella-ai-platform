# Bella AI Agents — Autonomous Execution

**Scope:** All AI work across Bella AI Platform, including Platform/Core, Factory, Industry OS, integrations, Shared UI, and every current or future Product.

**Authority:** Apply the [Constitution](BELLA_AI_CODING_CONSTITUTION.md), especially [Scoped Autonomy and Approval](BELLA_AI_CODING_CONSTITUTION.md#scoped-autonomy-and-approval), [Fast, Correct, Evidence-Based Execution](BELLA_AI_CODING_CONSTITUTION.md#fast-correct-evidence-based-execution), and applicable specialized rules. This is the shared operating instruction for autonomous execution; it creates no new workflow, gate, permission, or exception to those rules.

**Goal: complete the assigned outcome, not merely identify obstacles.**

1. **Own completion within scope.** Once the task and authorized scope are clear, analyze, implement, test, repair related failures, and verify through the scoped acceptance criteria. Resolve routine technical choices yourself. Do not ask the user to approve each step, repeat an applicable decision, or restate authority already granted. Respect the responsibilities of your assigned role.
2. **Investigate alternatives when a method fails.** Identify whether the cause is code, configuration, fixture, environment, contract, or access. Check existing sources and supported options, then use the smallest safe, compatible, recoverable alternative within authority. Prepare missing configuration or fixtures when permitted and supported by the test contract; never fabricate runtime data or expose secrets. Follow the Constitution's [bounded diagnosis](BELLA_AI_CODING_CONSTITUTION.md#bounded-test-and-environment-diagnosis): each further check needs a supported hypothesis or changed input. Do not repeat an unchanged failure indefinitely.
3. **Continue independent work.** Missing evidence is `NOT_PROVEN`; it proves neither a defect nor that all work must stop. Hold only the work that depends on the missing evidence or blocked capability. Complete other authorized parts without requiring proof of the whole system. A missing required acceptance criterion still prevents claiming the whole task complete.
4. **Stop at the actual boundary.** Investigate lawful alternatives before requesting help. Hold the affected action when necessary access or change authority is unavailable, a mandatory business/ownership/contract decision is unresolved, real data would be exposed to unauthorized or unsafe effects, or tools/policy prevent every permitted approach. Preserve Production protections, security, tenant isolation, frozen boundaries, and existing approval requirements. Never bypass a restriction or an explicitly held execution stage. Ask only for the specific decision, authority, or access that is necessary, with evidence and the smallest concrete proposal; continue independent authorized work.
5. **Do not turn obstacles into more process.** Reuse the current contracts, tooling, task records, and approved workflows. Do not add a contract, gate, report, approval loop, or framework unless the proven root cause and applicable authority require it. Safety and process are not reasons to stop early while a lawful approach remains available.
6. **Verify and report outcomes.** Run the applicable checks, fix failures within scope, and retain sufficient evidence in the existing task record or permitted evidence location. Report what changed, commands and actual results, evidence, unfinished acceptance criteria, and the specific cause of any remaining obstacle. Never report `PASS` without executed proof or treat `NOT_PROVEN` as a product defect. Seal the scoped result and stop when acceptance and mandatory applicable checks are satisfied.

**Root Cause → Minimal Fix → Verify → Seal → Stop.** Prioritize the completed business outcome with the smallest safe change and sufficiently reliable evidence.

For selected Factory work, apply [Factory Operating Rules](FACTORY_RULES.md). Operational readiness audits retain their [read-only SOP](OPERATIONAL_READINESS_SOP.md); implementation authority does not turn an audit into an unrecorded repair phase.

Keep this instruction shared. Product checklists and lessons should contain only evidence-backed Product differences, not copies of this rule. Use existing task evidence to assess necessary user interventions, avoidable stops, and completion from start to finish; documentation alone does not prove improvement or native Factory adoption, and no new CI, guard, or telemetry system is required.
