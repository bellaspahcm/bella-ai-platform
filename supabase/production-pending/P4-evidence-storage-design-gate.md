# P4 — Evidence Storage design gate

**Status: HOLD — the Production bucket, Storage policy and real upload path are not ready.** P3 separately proposes the service-role metadata RPC already called by the application; it does not create a bucket or authorize an object upload and remains unexecuted.

Production currently has no `interior-site-evidence` bucket. The existing customer-signature bucket is private and limited to 5 MiB; it is a separate purpose and must not be repurposed implicitly.

The minimal configuration supported by the current source is a private `interior-site-evidence` bucket with a 10 MiB limit and MIME types `image/jpeg`, `image/png`, `image/webp`, `image/heic` and `application/pdf`. The existing O3 migration also names this bucket for site evidence; P4 must account for both O3 and O4 before changing object access. O4 uses it for acceptance evidence, including the `CUSTOMER_SIGNOFF` category; the separate customer-approval signature bucket remains a different flow. These are source-based proposed settings, not a provisioned Production configuration.

The O4 route checks the actor's upload permission and session context, uses a trusted server client, and writes `{tenant}/{project}/acceptance/{session}/{uuid}-{filename}` with `upsert: false`. The metadata RPC checks the actor, session, permission and object path; its candidate has not run. Failed metadata registration attempts object cleanup. Retrieval policy and real upload/cleanup behavior remain unverified.

On 21 November 2026 the owner selected retention until deletion is requested, with OWNER/ADMIN permitted to request and execute deletion after checking contractual, legal and record-retention obligations; there is no automatic expiry. Failed-upload cleanup is separate from deletion of registered evidence. No retention duration or automatic purge was approved. The owner also decided to retain a shared file until its final evidence reference is removed.

For reads, the source now checks the actor's tenant, project and applicable O3/O4 read permission using the associated session or diary before downloading via the server. O4 supplies an evidence download link; O3 returns protected links for stored object paths prefixed by the correct tenant and project. O3 legacy URLs and paths without that prefix cannot safely be mapped automatically and are omitted. The historical O3 source migration describes a restrictive policy, but a fresh Production catalog read found that policy absent. The only current permissive Storage policies target a different bucket; the evidence bucket itself is absent. P4 therefore requires a dedicated restrictive client-access policy before bucket provisioning. Local read tests use mocks; Production behavior is unproven. No signed URL is issued.

Deletion source and review SQL now contain a scoped request, review reference and confirmation, OWNER/ADMIN execution, recorded events and pending/failed retry states. The draft counts references across O3 and O4, retains shared files, blocks new references while a deletion is active and recalculates O4 documentation after metadata deletion. It preserves request and event records after deletion. The SQL and its rollback are review drafts, not ledger migrations, and DB, Storage, concurrency and Production behavior remain unproven. If the DB is unavailable after a Storage operation, the prior pending attempt remains, but recording the specific failure stage requires a successful DB call. Legacy O3 URLs and repeated copies of the same path within one diary need reconciliation before deletion.

After that decision, provision through Supabase Storage controls/API. A later database migration may assert the already-provisioned bucket's privacy, size and MIME configuration and add narrowly scoped object policies/RPC. It must not insert or update `storage.buckets` directly or create a bucket just to satisfy a SQL preflight. Verify upload and denial cases through the actual Production API only after runtime identity and recovery are resolved.

`P4-storage-policy.review.sql` proposes the dedicated policy; it is not executed. Production `storage.objects` is owned by `supabase_storage_admin`; read-only catalog showed neither `postgres` nor `bella_migration_executor` is a member of that role and `postgres` is not superuser. The current Supabase MCP SQL session reports both `current_user` and `session_user` as `postgres`, so it does not establish the required owner authority. Supabase documents bucket creation through Storage API or Dashboard and policy administration through Dashboard Storage Policies; whether this project's Dashboard path can create the required `AS RESTRICTIVE` policy and its effective executor remain unverified. Do not grant managed roles or alter ownership. If that path cannot preserve the exact policy, obtain Supabase-supported owner guidance. The P4 deletion draft will abort if the reviewed restrictive policy is not in place.

Their ownership, availability and content have not been checked.
